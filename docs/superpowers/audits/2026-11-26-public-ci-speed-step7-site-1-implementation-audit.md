# Implementation audit: public CI speed, step 7 (merge queue), Site (cycle 1)

Verdict: **4176fc0 FAIL: 1 red**

**R1. The read-only `commit-authors` inside `gate` races the footer-stripping workflow, and can leave `gate` red with no way back but a push or a re-run.**

- What is wrong: on `pull_request` `opened` (and `reopened`, `synchronize`) both `ci` and the standalone
  `.github/workflows/commit-authors.yml` start. The in-ci job has `pull-requests: read` and runs the same
  `scripts/check-commit-authors.ts`, whose `withoutToolFooter` PATCHes the body to take off the tool footer and, when
  the PATCH is refused (`if (!response.ok) return body`, line 349), judges the body as it stands. So if the in-ci job
  reads the body before the standalone job has stripped it, the footer fails the in-ci job, and `gate` goes red.
- Evidence: the cloud tool appends `_Generated by [Claude Code](...)_` to every description it creates (the Owner's
  choice of 2026-11-17, in the standalone workflow's header), so every pull request a session opens starts with the
  footer. `ci` does not listen to `edited`, so the strip that follows does not start a new `ci` run: `gate` stays red
  until the next push. A pull request opened ready for review (no `ready_for_review` event follows) then never reaches
  a green `gate`, auto-merge never enqueues it, and the only way out is a re-run, which the rules count as a retry.
  `tests/workflows/merge-queue.test.ts` pins the job to read only (`expect(check).not.toContain(': write')`), so no
  test covers this ordering.
- Expected: `gate` does not depend on which of two parallel jobs reads the description first. The footer still may
  not reach `main`'s words unchecked.
- Bounded fix (one of):
  1. Give the in-ci job `pull-requests: write` on its job, as the standalone job has, so it strips the footer itself
     (fork pull requests get a read token either way and keep today's behaviour). Change the test's `: write`
     assertion to allow exactly `pull-requests: write`, and say why in the comment.
  2. Or have the in-ci job judge `stripToolFooter(body)` without writing (an env flag such as `READ_ONLY=1` that skips
     the PATCH), leaving the standalone job as the one that removes it, plus a unit test of that flag.
  Either way, add a test that a body ending in the tool footer passes the in-ci path.
